# ADR-009: The window thread never runs logic and never waits on another process

- Status: Accepted
- Date: 2026-11-13
- Requirements: FR-HK-003, FR-LIFE-003/004, NFR-REL-001..003, NFR-UX-001, architecture 5.8 and 11

## Context
A user reported the Focus screen freezing: no key worked and the machine had to be reset. The cause was not reproduced (the trigger is unknown), but reading the code showed how it can happen. One thread owns every overlay window, the selector and the hotkey registrations. Hotkey handlers, display-change handlers and selector events all ran *on* that thread, and they called into windows of other programs without a time limit: `SetWindowPos`, `GetWindowText`, `ShowWindow` and `SetForegroundWindow` on a frozen application wait for it. While that thread waits, the overlay cannot paint and `WM_HOTKEY` for Emergency Recovery is never dispatched, so the overlay stays and nothing can remove it. Other findings from the same read: the selector attached its input queue to the foreground thread (`AttachThreadInput`), which freezes keyboard and mouse for both if that thread hangs; the overlay manager held one lock across overlay creation and teardown, and the window thread could take it, so Show on one thread and Reconcile on the window thread could deadlock until a 10 s timeout; Emergency Recovery waited on that same lock.

## Decision
1. **The window thread only paints and enqueues.** Hotkeys, display changes and selector input are read there and handed to an ordered command thread (`Win32Thread.Post`). Emergency Recovery is handed to a thread of its own (`PostUrgent`), so it never queues behind a stuck command. Exceptions are contained in every window procedure; one that escaped would end the process.
2. **Calls into other processes are bounded or asynchronous.** Titles are read with `SendMessageTimeout` (250 ms, abort if hung); layering changes use `SWP_ASYNCWINDOWPOS` and `ShowWindowAsync`; windows for which `IsHungAppWindow` is true are neither listed nor revealed; one enumeration has a 3 s budget; `AttachThreadInput` is skipped for a hung foreground window and always undone.
3. **Emergency Recovery takes no lock that other work can hold.** `OverlayManager.Teardown` does not wait for creation; it bumps an epoch and a creation in flight disposes what it made and gives up. `FocusService.EmergencyRecover` isolates every step (a throwing subscriber or a dead window cannot stop the next step) and keeps the revealed set under its own lock. The selector close and the timer stop it triggers run on the thread pool.
4. **Windows lifted above the overlay are put back.** Revealing makes a window TOPMOST; Focus Off and Emergency Recovery now return them to normal layering, so a revealed window is not left always-on-top.
5. **Last line of defence.** A `HeartbeatMonitor` pings the window thread every second; five seconds without an answer means it is wedged. With Focus on, nothing in the process can recover that, so the host ends the process and Windows removes every overlay. Idle, it only logs. A gap between checks longer than about four seconds (sleep, starvation) re-bases the clock instead of reporting a stall.

## Consequences
Selector and hotkey handlers now run on a different thread from the one that owns the windows, so they marshal back with `Win32Thread.Invoke` (4 s limit). `SelectorController` serialises its state with a lock. The cost of the watchdog is that a genuine wedge ends VEIL instead of leaving a frozen screen; the agent has to be started again.

## Verification and open items
Unit tests cover the monitor, teardown during a stuck creation, Emergency Recovery during a stuck FocusOn, throwing subscribers, lowering of revealed windows. Live on the development PC: with an application whose UI thread was blocked, Focus Mode started normally, the frozen window was skipped, and a real `Ctrl+Alt+Esc` keypress restored the desktop in about 40 ms. **Not shown:** that the original freeze happens on the previous build under the same conditions (its trigger is unknown), and the watchdog's process kill has not been exercised live because no safe way was found to wedge the window thread. A freeze whose cause is outside this list (a graphics-driver or DWM fault, an elevated or secure-desktop window in front) is not covered; Overlay Focus remains a visibility feature, not a lock.
